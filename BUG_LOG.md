# Bug log

Every bug found while building CanaryJudge, with the tool or check that found it. Newest last.

| # | Date | Component | Symptom | Found by | Cause | Fix |
|---|---|---|---|---|---|---|
| 1 | 2026-10-04 | traffic splitter (routing) | In the first smoke run the canary served 5,421 requests and the baseline 4,313 although each had a 50% share | Splitter stats (`/admin/lanes/l1`) after the smoke run | Users are assigned by a hash of the user id, so a user always lands on the same side. The load generator draws users from a Zipf distribution, where the most active user alone sends about 9% of all requests, so whichever side that user hashed to got far more traffic. Unequal load moves CPU and latency, which an A/A comparison would read as a difference | Lanes have a mode: trial lanes split per request (equal load on both sides), the rollout lane keeps sticky users (needed to count how many users a canary reached) |
| 2 | 2026-10-04 | canary config (memory metric) | The first A/A run (identical baseline and canary) failed under every statistical judge, on `heap_used`: the canary's mean heap was 44% above the baseline's | `bench evaluate` on the first three recorded runs: Kayenta-style judge Marginal with `heap_used:High`, fixed Mann-Whitney p = 0.0, sequential judge fired after 10 intervals | Heap in use saws with every young collection, and old-generation garbage from start-up stays until a full collection, which happens at a different moment in each JVM. Two identical JVMs therefore differ by tens of megabytes for minutes, which is a real shift for any test | The metric is now heap in use right after the most recent collection (`cj_heap_after_gc_bytes`, from GC notifications), and every target runs one full collection when it is ready, so both sides start clean. The 9 runs recorded with `heap_used` are kept in `results/trials_v0_heap_used.jsonl` and not used |
| 3 | 2026-10-04 | traffic splitter (memory) | Trials stopped receiving traffic; `docker ps` no longer listed the splitter | `docker ps -a` and `docker logs cj-splitter`: `OutOfMemoryError: Java heap space`, container exited | Every trial removes two containers with requests in flight. Requests to an address that no longer exists wait for the 10 s timeout, so at 240 requests/s thousands of exchanges (with their buffers and virtual threads) piled up in a 160 MB heap. The load generator had the same unbounded pile-up | At most 2,000 requests in flight in the splitter (503 beyond that) and 1,000 per lane in the load generator, 1 s connect and 5 s request timeouts, 256 MB heaps with `-XX:+ExitOnOutOfMemoryError` and a restart policy. The trial runner now rejects (and re-runs) any trial in which either side's request rate dropped below 60% of its share in any interval, so a traffic outage can no longer produce a recorded run |
| 4 | 2026-10-04 | trial runner (scheduling) | With the splitter fixed, every run of the next check was rejected: in the first minute of each measurement window the request rate fell to 2 to 20 per second (expected 40) and the median latency rose to 150 to 300 ms | The new traffic check in the trial runner (bug 3), then the rejected runs' series and `/proc/loadavg` (28 on 2 vCPUs) | Lanes were started 40 s apart so their windows would overlap. But a Spring Boot start-up costs most of a CPU for a minute or more, and six JVMs on two vCPUs could not keep up; each lane's start-up landed in another lane's measurement window and starved it | Lanes now run in lockstep batches: all pairs start together, warm up together (90 s after the last one is scraped) and are measured over the same window, then all stop. The targets run with C1 only (`-XX:TieredStopAtLevel=1`), which cuts start-up compilation, and a lane's traffic is off while its containers are replaced |
| 5 | 2026-10-04 | canary config (memory metric) | With heap measured after GC (bug 2), both A/A runs of the next check still failed on `heap_after_gc` (canary 15% and 8% above an identical baseline), under the Kayenta-style judge, the fixed-horizon test and the sequential judge | `bench evaluate` on the check runs | Heap after a young collection still includes the old generation, which fills at its own pace in each JVM as surviving objects are promoted. Two identical JVMs settle at levels 5% to 15% apart, and the level moves slowly, so every interval in a run sits on the same side: a real, persistent difference to any test that treats intervals as samples | Memory is judged against a tolerated shift, which is what Kayenta's `effectSize.allowedIncrease` exists for: 1.25 for heap in the Kayenta-style judge, and the same margin in the sequential judge (it tests whether the log ratio exceeds log 1.25) and in the fixed-horizon test. Re-judged offline from the same recordings, both A/A runs pass and the 4 KB-per-request leak still fails. The cost is that leaks below about 25% growth over the window go undetected (exp1 reports how many) |
