# NUMBERS

Every figure CanaryJudge reports, generated by `bench/ledger.py` from `results/*.jsonl`. Each section names the file its rows come from.

**Machine.** One shared mini PC: AMD Ryzen 3 4300U with Radeon Graphics (4 cores), 16 GB, Windows 11 with WSL2 (2 vCPU, 5.8 GB). Every target, Prometheus, the splitter, the load generator and the judges run in that VM. Other jobs share the box, so each run records the host load: Windows host CPU 9% to 100% at the start and end of the runs, WSL 1-minute load 1.8 to 20.5.

**Workload.** A sample Spring Boot service (`target/`) whose requests wait on a simulated dependency (log-normal, median 20 ms) and fail at a 0.1% background rate. Each live canary is a fresh baseline and a fresh canary started together, each taking half of 80 requests per second from an open-loop load generator (Poisson arrivals, Zipf-distributed users), measured for 6 minutes after a 90 s warm-up, sampled every 10 s from 2 s Prometheus scrapes. Regressions are injected into the canary. Not production traffic and not a production service.

## The recorded runs (`results/trials.jsonl`)

58 live canary runs: A/A (no change) 18, calibration 2, CPU +1 ms per request 2, CPU +4 ms per request 2, errors +0.5% of requests 7, errors +2% of requests 2, latency +10% 3, latency +2% 4, latency +25% 3, latency +5% 5, latency +50% 3, leak 1 KB per request 3, leak 4 KB per request 4. The calibration runs only set the tuned static thresholds and are not scored. Runs rejected for losing traffic are in `results/trials_rejected.jsonl` (if any) and were re-run.

## exp5: live rollouts (`results/exp5.jsonl`)

The rollout controller moves a fresh canary through 1%, 5% and 25% of users (2 minutes each, a fresh baseline at the same share), then promotes it. Users stick to one side by a hash of their id; the share of users who reached the canary is counted by the splitter from the start of the rollout to the end (rollback or promotion).

| regression | judge | rollouts | rolled back | median minutes to rollback | median share of users reached | max share of users reached |
|---|---|---|---|---|---|---|
| errors +2% of requests | fixed | 1 | 1 | 4.1 | 3.39% | 3.39% |
Manual 30-minute canary, for comparison (a model, not a measurement): a canary at 5% of users for 30 minutes exposes 5% of users when the regression is caught at the end, and every user when it is missed and promoted. With the miss rates of the tuned static limits from exp1 (the closest thing to a person watching dashboards), the expected share is listed per regression in `results/exp5_manual_model.jsonl`.

## A/A simulation: peeking versus the sequential test (`results/sim_aa.jsonl`)

Synthetic healthy canaries (not live data): per-interval latency for baseline and canary from the same log-normal, with a load term shared by both sides (or none), and AR(1) noise with autocorrelation phi. A shared load term makes the unpaired Mann-Whitney test conservative (it ignores the pairing); with independent sides it sits at its nominal 5%. One metric, one-sided, alpha 5%.
